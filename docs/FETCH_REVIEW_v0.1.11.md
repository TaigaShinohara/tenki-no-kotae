# 厳格レビュー（データ取得まわり限定）— 天気のこたえ v0.1.11

実施： 2026-11-20。本人の指示「天気のデータの取得について厳しくレビューして。特に安全性や安定性、速度について」。
方法： パソパソ側監査と独立審査（過去レビューを読まない）の2系統を並行実施し、照合・統合した。
今回は洗い出しまで（修正は本人の判断待ち）。コードは無変更。

総評： 典型的な安全性の穴（平文通信・証明書検証の無効化・URL注入・個人情報の送信）はゼロ。
弱点は「上限の効かせ方」（応答サイズ・予算・スレッドの寿命）と「キャッシュの使い方」に集中する。
統合件数： 20件（致命的 0／重大 0／中 7／小 13）。うち新規 15件、既知の再確認・未解消 5件。

## 確認して問題なかった点
- HTTPS のみ＋ usesCleartextTraffic="false"。証明書検証を弱めるコードは全ソースに無し。
- URL は固定8都市の定数からのみ組み立てられ、利用者入力が入る経路は無い（注入の余地なし）。
位置情報は GPS ではなく都市の選択式で、送信されるのは選んだ都市の座標だけ。
- 世代管理（v0.1.11）は全経路で効いており、古い取得が画面・キャッシュを上書きする余地は塞がれている。
- MET Norway の識別 User-Agent 要件は満たしている。gzip の要求・解凍は実装済み。
- disconnect() は finally で必ず実行され、接続リークの経路は見当たらない。

## 中（確実）

1. 【解消済み v0.1.12 → docs/FIX_v0.1.12.md】応答の読み取りと gzip 解凍にサイズ上限がなく、巨大・異常な応答で OOM クラッシュし得る。
成功経路・エラー経路とも readText() で全量を載せる。WeatherApi.httpGetText（両系統一致）
2. 【解消済み v0.1.12 → docs/FIX_v0.1.12.md】旧世代の取得スレッドは誰も止めず、予算いっぱいまで通信し切り、連打で積み上がる。
世代チェックは完了後にしか効かない。無料APIへの自己発の集中アクセスになり 429 を誘発し得る。
MainActivity.loadWeather（両系統一致）
3. 【解消済み v0.1.12 → docs/FIX_v0.1.12.md】キャッシュは失敗時の代役専用で、正常時には一切使われない。
数分前のキャッシュがあっても開くたびに全量再取得し、スピナーが回る。HTTP キャッシュ（ETag 等）も未使用。
MET の利用条件（キャッシュ活用・再要求抑制）との相性も悪い。MainActivity.loadWeather（両系統一致）
4. 【解消済み v0.1.12 → docs/FIX_v0.1.12.md】1回の試行は「接続＋読み取り」がそれぞれ残り予算で頭打ちされるため、
残り予算の最大約2倍まで伸びる。全滅時の理論最悪は約65〜80秒で、「約1分以内」は構造的に保証されていない。
WeatherApi.fetchWithBudget（両系統が再計算で一致）
5. 【解消済み v0.1.12 → docs/FIX_v0.1.12.md】429（レート制限）と 408 も「決定的な 4xx」として即打ち切り、Retry-After を読まない。
一時的な制限で健全な主源を見限る機会が増え、予備源も失敗した時に主源へ戻る道がない。
WeatherApi.fetchWithBudget（両系統一致）
6. 【解消済み v0.1.12 → docs/FIX_v0.1.12.md】フォールバックが完全直列で、主源が「遅いだけ」の日は予算を使い切るまで予備源が始まらない
（ヘッジなし）。FIX で採用した予算方式の裏側の特性。MainActivity.loadWeather

## 中（疑い）

7. MET Norway の利用条件との最終整合が未確認（complete エンドポイントの常用、
再要求抑制の仕組みなし）。現行の条件文面での照合が必要。MetApi 全般

## 小（確実）

8. パースが両極端： 1変数の欠落でデータ源全体が例外死する一方、配列の長さ不足は 0.0 の
「それらしい嘘の値」で素通りする。WeatherApi.parse / MetApi.parse（既知 #24 の再確認を含む）
9. finally の disconnect() が接続の再利用（キープアライブ）を妨げ、試行ごとに TCP＋TLS を払い直す。
WeatherApi.httpGetText
10. User-Agent のバージョン表記が 0.1.3 のまま（既知 #18）。WeatherApi
11. allowBackup="true" で取得キャッシュ（地点ごとの応答全文）がクラウドバックアップ対象になる。
中身は公開天気データのみで機微度は低い。AndroidManifest
12. サーバー由来のエラー文字列が無加工で画面に出る。JSON 経路の reason には長さ上限がない
（プレーン経路は120字・「<」除外の歯止めあり）。WeatherApi.extractErrorReason / MainActivity.showError
13. ACCESS_NETWORK_STATE を宣言しながら未使用（オフラインの即時検知なし、死んだ権限）。AndroidManifest
14. 予備源 MET の "complete" が必要量に対して過大（約10日分・MB級を使うのは数日分）。
回線が苦しい場面ほど重い応答を落とし切る必要がある。MetApi
15. 取得抑制（最小間隔）も条件付きリクエストもなく、起動のたびに両源へフルリクエストが飛ぶ。
WeatherApi / MetApi fetchText
16. 破棄済み Activity への Toast 経路が残っている（configChanges で回転は止まったが、
画面を閉じた場合の確認がない）。既知 #11 の再確認。MainActivity.loadWeather

## 小（疑い）

17. キャッシュ鮮度判定が壁時計（currentTimeMillis）依存で、端末時刻の手動変更で鮮度が狂う。MainActivity
18. DNS 解決の時間がタイムアウト管理外で、予算を超えて待つ可能性がある（実装依存・未実測）。httpGetText
19. Open-Meteo の forecast_days=3 の3日目が未使用なら過剰取得（全利用箇所の数え上げは未実施）。WeatherApi
20. Open-Meteo 無料枠の商用条件 — ストア公開の段階では有料プラン／API キーへの移行が条件になる見込み
（設計段階からの既知の確認事項）。WeatherApi 全般
